# ADR-024: Advisory event-time risk features and model export

- **Status:** Accepted
- **Date:** 2026-11-04
- **Deciders:** varunpathania86

## Context

Stage 7 requires a reproducible logistic-regression baseline, a later LightGBM
comparison, ONNX inference inside Flink, model-registry artifacts and
audit-preserving late-event prediction revisions. Stage 6's input has no
account-age/device context. The maintainer approved optional synthetic fields
and single-cluster low-memory live validation; three-cluster acceptance remains
resource-limited. No score may authorize, reject or block a payment.

## Decision

Extend the existing processing contract compatibly with nullable
`account_created_at` and synthetic UUID `device_id`, both defaulting to null.
Compute account age at event time and device changes from prior history, never
from wall-clock time or a future payment. Missing context is unknown, not safe.
Version numeric/categorical names, order, dtypes, missing handling,
preprocessing and advisory outputs in the model's feature contract.

Build prior-history features within the same account and currency to avoid
summing unrelated monetary units. Histories use strict `(event_time, event_id)`
ordering for deterministic ties; 10-minute activity and one-hour reference
history exclude the current outcome and all future events. Device/country flags
are descriptive reasons, not causal model explanations.

Train only on synthetic data, split by held-out accounts, and retain the
logistic-regression baseline as the selected artifact. Evaluate LightGBM
after establishing the baseline, without automatic promotion or tuning on the
held-out set. Record imbalanced-class metrics, inference-only latency and
model size. Validate ONNX graphs and both held-out/golden parity at absolute
tolerance `1e-5`; do not commit generated model binaries.

Package the baseline, shared features, contract and golden vectors into a
versioned Python ZIP. Publish artifacts to MinIO with conditional, immutable
per-object writes; retries accept only identical content. Submission pins an
explicit versioned key and ZIP SHA-256, validates package shape/size, and
distributes it through Flink `--pyFiles`. Operators verify model metadata and
golden scores and create one reusable ONNX Runtime session in `open()`.

Maintain checkpointed history per account/currency. An accepted late event
recomputes affected later feature vectors within one hour; changed vectors
emit new prediction identities/revisions preserving `original_prediction_id`.
Retain original records in a noncompacted, at-least-once Kafka audit topic;
downstream consumers deduplicate deterministic prediction IDs. Expose counters
under the model version. Keep scores outside payment authorization, while
acknowledging a failing scoring branch can restart the shared analytics job.
Changes to model pins require explicit stop/savepoint/restore. Both affected
model and Flink CI paths run real-worker three-way golden parity.

The SQL result sink previously relied on autogenerated operator hashes.
Optional branch addition changed those hashes even when that branch was appended
after SQL translation. Preserve the baseline writer/committer hashes through
Flink's custom sink hash migration API before adding risk operators. Do not
silently allow non-restored state. Real graph identity tests cover analytics
on/off, and live acceptance must restore the pre-risk savepoint.

## Alternatives considered

| Option | Pros | Cons |
|---|---|---|
| Current event fields only | No contract addition | Cannot demonstrate account age/device context |
| Required enriched fields | Simpler complete inputs | Breaks older producers and invents unavailable context |
| Optional synthetic fields | Backward-compatible, realistic missing context | Requires explicit validation/imputation |
| Current outcome as a feature | Easy apparent discrimination | Target leakage and misleading evaluation |
| Auto-select highest accuracy | Simple headline result | Wrong objective for rare suspicious labels; overfits evaluation |
| Score-driven payment blocking | Superficially complete fraud product | Outside scope and violates advisory-only boundary |

## Consequences

Old processing producers remain valid; new producers can supply explicitly
synthetic context. Some numeric missing values are median-imputed, with explicit
account/device missing-context flags retained. ONNX converter support ruled
out implicit imputer-generated indicators in this pinned stack; named flags
keep the contract and conversion shape explicit.
Full held-out parity also exposed scaler arithmetic differences at tree split
boundaries. Export uses explicit subtraction/division rather than a fused ONNX
Scaler, and categorical output uses float32 to match the numeric input contract.
The `1e-5` parity tolerance was not relaxed to hide those differences.

The generated label process intentionally encodes constructed patterns:
metrics do not estimate real-world fraud performance. The initial fixed
0.5 threshold has weak minority-class recall and must not be presented as an
effective fraud policy. A later calibration/threshold experiment needs
separate training/validation/test data, not tuning against this held-out set.
No new ML service or payment-critical dependency is introduced.
